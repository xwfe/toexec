# V2-P0：Claude 经 exec-server 试验的基线与冻结判据

日期：2026-09-17。属于 [v2 计划](implementation-plan-v2.md)第 8 节的 V2-P0，回答第 3.2 节的问题。**本文的第 3–9 节在任何候选运行之前冻结**；V2-P1 的结论只能按这里写的判据下，要改判据必须先改本文并说明原因，不能看了结果再调。对照组（直接执行）的实测结果写在第 10 节，它不是候选，冻结前后测都不影响判据。

## 1. 这一步做什么、不做什么

做：定下 V2-P1 要比较哪几条路径、用同一套什么夹具和命令、测哪些开销、什么结果算"值得继续"；把对照组（今天的直接执行路径）实测一遍，保证基线能按脚本重建。

不做：不跑任何候选路径；不写产品代码；不改任何机器上的配置；不装东西；**模型额度 0 次**。

## 2. 要回答的问题

Claude 的执行请求如果改由官方 `codex exec-server` 执行，多出来的**操作系统层约束**，是否值得多出来的部署、协议、版本和 RPC 成本？只由 MCP 参数校验挡下的请求不算新增约束——那在直接路径上本来就挡着。

先说一个已知前提，免得读者以为直接路径有沙箱：ccnm 的 `exec_command` 按 argv 直接起进程，**没有任何 OS 沙箱**（`crates/ccnm-core/src/mcp/exec.rs` 开头写明"This is not a sandbox"），它的安全完全靠 Runtime 的专用执行账号。所以候选能带来的新增约束，只可能来自 exec-server 给命令套的 Codex 沙箱（macOS 是 Seatbelt，Linux 是 bubblewrap）。

## 3. 对照与候选

| 代号 | 路径 | 用途 |
| --- | --- | --- |
| **D** 对照 | 中立 MCP 客户端 → `ccnm internal mcp-serve`（受管 open，coding）→ `exec_command` / `read_file` / `read_output` | 今天 Claude 实际走的路 |
| **A-proc** 候选 | 中立 exec-server 客户端 → `ccnm internal exec-serve` → `codex exec-server`，`process/start` 带 Codex 0.154.0 的 workspace-write 沙箱 | 进程委派。`exec-serve` 是 ccnm P22 的现成产品代码，规则表强制带沙箱、拒绝提权，不需要为试验写产品代码 |
| **A-read** 候选 | 同上链路，`fs/open` / `fs/readBlock` / `fs/close` | 分块读委派 |
| **S** 替代 | `codex sandbox`（0.154.0 自带的子命令）包住与 D 相同的 argv，不经 RPC | 判断约束来自沙箱本身还是来自 exec-server。S 能给出同样约束时，A-proc 的 RPC 和协议维护就不是得到约束的必要代价 |
| **N** 隔离对照 | 裸 `codex exec-server`，`sandbox: null`，只在临时目录、合成数据上跑，不经 ccnm | 只在 A-proc 确有新增约束时跑，用来把 RPC 开销和沙箱作用分开 |

A-proc / A-read 若被采纳，产品形态是"Runtime 上的 ccnm MCP 工具内部改调本机 exec-server"：模型看到的仍是 `exec_command` 和每页 64 KiB 的 `read_file`，RPC 走 Runtime 本机管道。所以测量时客户端和 exec-serve 在同一台机器上，这正是那一跳的真实位置。

## 4. 固定版本与二进制取得

| 对象 | 固定为 | 怎么取、怎么核对 |
| --- | --- | --- |
| ccnm | 跑测时 `ccnm` 仓库的 HEAD 与所用二进制的 sha256，由 `evidence/v2-p/p0/baseline.py` 写进结果 | 本机从源码构建。P1 必须用与 P0 结果里 sha256 相同的二进制，或者重跑 P0 |
| exec-server 后端 | Codex **0.154.0**（与 ccnm 原生链锁定的是同一个版本）。macOS：Homebrew 的 `/opt/homebrew/bin/codex`，sha256 记进结果；Linux：官方 musl 发行包，包 sha256 `d7e18b25…`（ccnm P24 记录） | 一律用绝对路径，**不跟随 PATH 上的 `codex`**。GitHub 下载慢时在链接前加 `https://git.yylx.win/` 加速，下载后必须核 sha256 |
| 客户端 | Python 3 标准库，不 import ccnm 或 Codex 的任何代码 | 与 ccnm P24 的中立客户端同一做法 |

Codex 升级不等于要换：Claude 试验若被采纳，可以独立 pin 后端；但 exec-server 协议没有版本协商（toexec G01），**换任何版本都要重跑 V2-P1 的探针和 ccnm P21 式的请求核对**，这个成本计入第 8 节。

## 5. 平台范围

P1 先在 **macOS arm64 本机**跑（账号 `bing`，不是专用执行账号；Runtime 的 HOME 和状态目录用运行目录下的临时目录，理由同 ccnm exec_serve 集成测试：不这样凭据审计会整会话拒绝）。结论**只对测过的平台成立**。Linux 那一组要么在本机 OrbStack 容器里做（启动会顺带拉起用户的其他容器），要么在 hpsrv 上做（P24 的一次性公钥已撤），两者都要先征得用户同意，不在 P1 的默认范围内。任何候选在进入 V2-P2 之前必须补 Linux。

## 6. 夹具（`baseline.py` 生成，所有路径共用）

- **运行目录不能在 `/tmp` 或 `$TMPDIR` 下**：沙箱通常允许写临时目录，"工作区外"的 canary 放在那里什么也证明不了。脚本发现在临时目录下会直接退出。
- `workspace/`：git 仓库，含 `src/app.py`、`README.md`；`data/` 下是 V2-G03 的读取样本（空文件、BOM、CRLF、无尾换行、非法 UTF-8、跨 64 KiB 与 1 MiB 边界的三字节字符、8 MiB 单行、8 MiB 多行；128 MiB 多行按需生成、用完删除）。
- `outside/canary.txt`：工作区旁边、执行账号可读写的合成 canary。
- Runtime HOME 下的 `.p0-canary`。
- `/private/tmp/v2-p0-*`：临时目录写探针的目标，跑完删除。
- 网络目标只有脚本在 `127.0.0.1` 上开的一个监听端口，记录每个探针发来的字符串。**不连任何外部主机。**

## 7. 探针

每个探针跑 5 次，每次都用磁盘、监听端口或输出内容核对副作用是否真的发生，不看退出码下结论。

| 探针 | 类别 | 做什么 |
| --- | --- | --- |
| W1 | 合法 | 在工作区里写文件 |
| W2 | 约束 | 在 `outside/` 写文件 |
| W3 | 约束 | 在 Runtime HOME 写文件 |
| W4 | 约束 | 在系统临时目录写文件 |
| W5 | 约束 | 直接写工作区的 `.git/` |
| R1 | 约束 | 用命令读 `outside/canary.txt` |
| R2 | 约束 | 用命令读 HOME 下的 canary |
| N1 | 约束 | 连本机监听端口并发一串标记 |
| L1 | 合法 | 跑工作区里的 Python 代码 |
| L2 | 合法 | 在工作区里 `git add` + `git commit` |
| L3 | 合法 | 用命令读工作区文件 |

A-read 另跑文件 RPC 版本：`fs/open` 工作区外路径、`.git` 上溯、symlink 穿越。这些被 ccnm 规则表拒绝属于参数校验，**不算新增约束**，只核对没有比 D 放得更宽。

**什么算一条"新增约束"**，四条同时满足：D 上副作用 5/5 发生；候选上 0/5 发生；候选的阻止来自执行端的 OS 沙箱（证据是命令自己的报错，如 `Operation not permitted`，而不是 ccnm 回的 `-32600`）；同一轮里 W1、L1、L3 在候选上 5/5 成功（排除"什么都跑不了"造成的假约束）。

## 8. 开销测量方法

| 编号 | 测什么 | 方法 |
| --- | --- | --- |
| M1 | 起一个进程的往返 | 连续 50 次 `/usr/bin/true`，记 p50、p95；做 5 轮取中位数 |
| M2 | 大输出 | 一条命令输出 64 MiB：①模型看到结果（D 是预览，候选是适配层收完输出并截出同样预览）的墙钟、两个方向的字节数、服务端进程树峰值 RSS；②把输出全部取回的同样三项。5 轮 |
| M3 | 分页读文件 | 按工具消费者的方式每页 64 KiB 读完 8 MiB 多行、8 MiB 单行各 5 轮，128 MiB 多行 1 轮；记墙钟、调用次数、字节数、峰值 RSS。候选按"每页一次 open + readBlock + close"模拟适配层 |

峰值 RSS 每 50 毫秒采样一次服务端进程树（D 是 `mcp-serve` 及其子进程；候选是 `exec-serve`、`exec-server` 及其子进程）。ccnm 一律用 **release 构建**：debug 构建慢一个数量级，会把 ccnm 自己的耗时放大成"RPC 看起来很便宜"。

**耗时只在同一时间窗里比。**（2026-09-17 补充，早于任何候选运行：第一次跑对照组时本机负载平均值是 102，同一台机器上别的会话、浏览器都在抢 CPU。）V2-P1 里 M1–M3 按 D、候选、D、候选……交替跑，每个测量块前后记录负载平均值；第 9.2、9.3 节的耗时阈值只用这种交替数据判定。本文第 10 节的对照组耗时只作参考和"脚本能跑通"的证据，不作阈值的分母。探针结果不受负载影响，照常有效。

## 9. 冻结判据

### 9.1 安全否决（任何一条出现，候选直接否决）

- 任何在 D 上被挡住的请求，在候选上成功了（包括 ccnm 规则表层面的读写范围）。
- 会话结束后有候选起的进程残留，或写锁在没证明进程结束时变成 `released`。
- 合法探针在候选上写到了预期之外的位置。
- 发给子进程的环境比 D 多出凭据类变量。

### 9.2 A-proc 值得进入 V2-P2 的条件（全部满足）

1. **至少一条新增约束**（第 7 节的定义），在 W2、W3、W5、R1、R2、N1 里算；W4 单独成立不够——临时目录可写是多数沙箱的默认。
2. **S 给不出同样的约束集合。**S 挡住的探针包含 A-proc 挡住的全部时，A-proc 相对 S 的增量为零，A-proc 不继续；S 记为一条单独的建议，由用户决定是否另立阶段，不自动采纳。S 的参数必须与 `exec-serve` 接受的沙箱等价，P1 写明等价依据；做不到等价就写"不可比"，结论里照实说。
3. **合法操作不退化**：W1、L1、L3 5/5。L2（git 提交）失败要单独记为退化；这种情况下 A-proc 不能替代现有 `exec_command`，最多成为并存的 opt-in，这是产品范围变化，交给用户决定。
4. **运行开销**（权重只占 10%，所以取宽松绝对值）：M1 的 p50 比 D 多 ≤ 100 ms、p95 多 ≤ 300 ms；M2 ①的墙钟 ≤ D 的 2 倍再加 1 秒；服务端峰值 RSS 比 D 多 ≤ 128 MiB。
5. **部署与维护**：后端必须是原生链已经锁定的那一个 Codex 版本，不引入第二个版本；没跑原生链的 Runtime 上要新装 Codex（约 100 MB，Linux 另需 bubblewrap），这种情况下要求新增约束 ≥ 2 条才算抵得过；产品适配层预估非测试代码 ≤ 1000 行，且复用 `exec-serve` 的规则表，不写第二份。

### 9.3 A-read 值得进入 V2-P2 的条件（满足一条即可，且不违反 9.1）

1. 出现一条 D 没有的读取约束（按第 7 节定义，参数校验不算）；或者
2. G03 样本上读出的内容与 D 逐字节一致，同时 M3 每页墙钟 ≤ D 的 70%、峰值 RSS 不高于 D。

预期是两条都不满足：D 的读取已经走 toexec-text 的有界读取，ccnm 规则表对两条路径的读范围相同。预期不等于结论，照样要测。

### 9.4 P1 的输出

只能是下面之一，并附每条判据的实测值：**维持直接执行**；**仅继续验证进程/沙箱**；**继续进程加分块读**。另外可以附一条"S 值得另立阶段"的建议。候选被否决也算 V2-P1 完成。
