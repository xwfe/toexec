# toexec / gld / ccnm：重构方向评审与收敛计划

日期：2026-09-19（Asia/Tokyo）

性质：**代码与现有证据审查后的实施建议，不是功能交付记录，也不是部署授权。**

位置：toexec 已承载跨仓 v2/v3 方案，故主评审放在这里；这不意味着 toexec 要成为控制面或调度产品。

## 1. 总结：方向正确，但要把重构重心从“继续补工具”转向“执行一致性”

不建议合并三个项目，不建议恢复 Codex 原生 exec-server 主线，也不建议另建通用 Workspace Server。当前最有价值的分工是：

| 项目 | 应坚持的定位 | 不应继续长进去的东西 |
| --- | --- | --- |
| **toexec** | 两个消费者确实共用、可独立测试的 Rust 机制库 | 账号、授权策略、MCP 服务、workspace 注册、模型循环、业务任务状态 |
| **gld** | 外部 AI 使用的多工作区开发入口；管理本地执行资源，受控转发远端 ccnm | 自建 Agent 推理循环、复制 ccnm 的 SSH/身份体系、另起一套跨产品规划器 |
| **ccnm** | 官方 Agent 的受管执行，以及具有明确身份、权限与生命周期的远端 Runtime | Planner/Router、任务图、自动 review/retry、跨 Agent/worktree 编排 |

**应保留的重构决策**：共享库只抽真实重复；官方 Agent 与项目执行分离；AI 登录留在 Agent；gld hub 经 ccnm 公共入口调用远端；本地与远端不伪装成完全相同的执行语义；失败后不偷偷换后端重放；代码、真机证据、部署状态分开记录。[S1–S6]

**需要调整的不是产品目标，而是实施顺序和保证边界。** “达到原生工具能力”应拆成能力覆盖、行为语义、权限边界、完整开发闭环四个维度。不能靠工具数增长、相同参数名或离线测试总数宣布完成。先修会丢数据的底层行为，再统一资源所有权、能力协商和任务生命周期，最后做剩余能力与真实用户流程。[S2–S8]

## 3. 应明确固定的跨项目所有权

```text
外部 Web AI / IDE / CLI
          │
          └─ gld：认证、workspace 授权视图、路由
                 ├─ 本地执行资源所有者 → 本地文件 / 进程 / 输出
                 └─ 远端适配器 → ccnm 公共 bridge → Runtime

官方 Claude Code / Codex
          └─ ccnm 受管会话或外部 MCP 入口 → Runtime

gld 本地实现 ─┐
              ├─ toexec：有界文本、文件替换、skill 解析等纯机制
ccnm Runtime ─┘

未来独立 Orchestrator：决定谁做什么、如何 review/retry/worktree 编排；
只调用公开执行接口，不进入上述库或 Runtime 的内部状态。
```

| 对象 | 最终权威 | 必须避免的双重所有权 |
| --- | --- | --- |
| 模型登录与推理 | 官方 Agent / 外部 AI 产品 | gld 或 Runtime 替 Agent 保存、搬运登录凭据 |
| 本地执行资源 | gld 内部统一的 workspace Runtime 所有者 | hub 与单项目 listener 分别持有互不知晓的进程表 |
| 远端执行身份、写权限、进程事实 | ccnm Runtime | gld 根据 HTTP 超时擅自认定远端命令失败或未执行 |
| 对外授权视图 | gld 请求主体与 workspace grant；ccnm 自己的身份/策略边界 | 共享执行上下文时顺便共享某个 endpoint 的认证上下文 |
| 业务计划与跨 Agent 调度 | 当前产品已有计划机制 / 独立 Orchestrator | 再建第三份 Goal/Plan/Task 权威表 |
| 验收与部署事实 | 对应仓库证据、实际运行构建 | 根据一个仓库的完成标记推断所有机器已更新 |

同一物理目录被 gld 本地成员与 ccnm 同时登记时，**不能因为都依赖 toexec 就认为已经共享写锁**。近期选择一个执行权威，另一入口转发或拒绝重复写注册；只有出现真实需求，才设计跨产品共同遵守的锁域。不要以一个所有人可写的锁目录代替身份隔离。[S6–S8]

## 4. 优先处理的问题

### X01 / P0：共享文件替换的 Windows 分支可能先丢掉旧文件

**源码确认**：`toexec-fs/src/atomic.rs::replace` 在 Windows 下先 `remove_file(target)`，再 `rename(temp, target)`。如果后一次重命名失败，旧目标已经被删。这不只是“不是原子操作”的体验差异，而是失败可能丢失原文件。[S1]

代码注释以“Windows rename 不能覆盖已有文件”为依据，但当前 Rust 标准库文档明确描述了替换已有目标及 Windows 平台实现差异，不能继续用这句笼统假设支撑删除行为。**本轮没有在 Windows 复现，也没有完成 Rust 1.89 目标环境验证；修复必须补这些证据，而不是照着当前文档直接宣布所有文件系统原子安全。**[R1]

建议：先立“替换失败保留旧目标”的不可退让约束，再按 MSRV 和目标 Windows/文件系统验证直接替换能力；确有缺口再评估小范围平台实现。不允许用先删后试的 fallback。gld 已有 Windows 发布构建，所以这一项不能等 ccnm 的 Windows RFC 才处理。

同时分清三种保证：单文件名称切换的原子性、内容/元数据的持久性、多文件提交的恢复能力。当前 `write_durable` 在同步内容后通过路径设置权限，没有同步父目录；README 的固定 `.tmp` 示例也不能作为面向不可信目录的安全临时文件方案。新增安全接口时评估独占临时文件创建、持有文件句柄设置权限、同文件系统替换及可选目录同步，保留各产品自己的事务与恢复编排。[S1]

**验收**：目标已存在、临时文件缺失、替换被拒、目标被占用、权限保留、遗留临时文件等情形都有断言；失败后旧内容不消失。只做跨平台编译不算 Windows 验收，不把多文件补偿回滚称为对任意外部读写者的原子事务。

### X02 / P0 收口：版本保护不能把“未知”当“不存在”

**源码确认，起始为未提交修改，收尾已进入 `70fb4a7`**：`current_file_version` 仍将 `metadata` 的各种错误统一变成 `None`，而补丁逻辑又把 `None` 用作文件不存在/已经删除的事实。无法读属性、I/O 错误与不存在必须分开；否则前置条件的安全意义被削弱。[S7]

当前 token 是 size + mtime，不是内容摘要。恢复原时间戳、时间戳精度差异、读取期间发生修改，都不能靠“纳秒精度所以不会漏”排除。两个产品无需拥有外观相同的 token；调用方应将它视为不透明值，原样交回同一资源与语义域。不要为避免额外整文件读取而谎称强 CAS，也不要为追求 hash 强制每次部分读取都扫描大文件。[S7–S8]

建议将元数据查询改成 `存在 / 确认不存在 / 查询失败` 的显式结果；删除、新建、读取后更新分别定义前置条件。继续保留已有提交前内容复核。新实施记录已经明确它与最终替换之间的竞态边界、没有宣称强 CAS，应承认这部分已考虑。`expected_versions` 的源码 schema、说明和回归也已补；后续只核对真实运行服务能否暴露和使用，并补尚未覆盖的三态等用例。

**验收**：权限或 I/O 错误不当作删除；同大小且恢复 mtime 的修改、读取期间修改、新建竞态、删除后重建、多个文件部分前置条件、未知参数都有测试。冲突返回要求重读，不自动按新版本重放旧补丁。此项合并到 gld 既有 U 系列/C3 写保护工作，不新起第二套 patch 引擎。

### X03 / P1：共享函数不等于共享执行资源和写权限

**源码确认**：gld hub 的 `context_for` 自行缓存 `ToolContext`，每次构造又创建 `SessionStore`；单项目入口也有自己的上下文构造。当前补丁中的进程级 Mutex 只覆盖该进程的补丁提交，既不是跨进程锁，也不协调普通 `exec`、Git、外部编辑器。[S6–S7]

建议沿既有 L1 路线，将 workspace 执行资源所有权从认证视图/工具 profile/提示词上下文拆开。多个入口引用同一个资源所有者，不是简单把带 `auth` 的完整 `ToolContext` 放进全局缓存。规范化目录、别名、嵌套 root、不同 state home 和不同进程的重复注册要有规则。

ccnm 已有 OS 文件锁加持久 `held` 标记，不能当作缺失重写。其锁路径受 state 目录影响，资源键优先取 Git common directory；因此要补“同一目录不同 state authority 不得形成并行写域”的部署约束。现有 common-dir 级锁会把相关 worktree 一起串行化，这是保守安全选择；未来 Orchestrator 要并行 worktree 时另设计工作树文件与共享 Git 元数据的两级协调，不在本轮随手放开。[S8]

**验收**：两个客户端、hub/单项目交错调用、两个进程和目录别名不能形成隐藏的第二写者；共享资源不允许跨主体读取任务输出。外部不合作写者仍需冲突检测与明示边界，不能宣传完全隔离。

### X04 / P1：远端后台命令与 hub 空闲回收存在组合风险

**源码确认**：gld coding 空闲阈值是 120 秒，判据是连接最后调用时间与调用锁；ccnm P41 的后台命令在启动返回后继续运行，但连接结束会停掉它。**推导风险**：模型启动后台任务后思考或用户停顿超过两分钟，hub 可能将连接当作空闲回收，从而结束仍在运行的命令。本轮未运行这一长时组合复现。[S5–S6]

首先明确四个不同的时钟：单次等待、命令运行期限、会话租约、输出保留期限。50 秒的 `wait_ms` 上限解决的是 60 秒调用预算，不解决 120 秒空闲回收；无限延长 RPC timeout 也不等于可恢复任务。

近期保留 ccnm 现有 **session-bound** 模式：取消/断开即清场，返回实际状态。gld 应明确展示租约期限，定义续租和活跃 Job 对回收的影响；续租必须有授权与总预算，不能后台永续占锁。更长远的 **durable Job** 是另一种显式协商的生命周期，不得将 `/1` 的断开即停悄悄改成断开继续。

gld 可维护远端 Job 的观察投影，但进程终态以 Runtime 为准。请求失败或 SSH 中断要保留“结果未知”，写操作不得重放；重连不复用上一代句柄。后台 `exec` 与同会话 `apply_patch` 的并发也要评估：会话之间单写者并不等于会话内部没有格式化器、构建脚本与补丁竞争。开发服务器可以有明确的并行工作流，但项目脚本自称只读不能作为授权依据。

**验收**：后台运行超过 coding 空闲阈值、等待超预算、取消等待与取消命令、重复 stop、传输重连、主体撤销和服务退出分别得到既定结果；任务要么在有效租约内继续，要么明确因租约终止，不能静默消失。使用可控制时钟的回归加真实二进制组合验证，不只改文字。

### X05 / P1：异常退出有写锁兜底，但没有完整的进程清理保证

ccnm P41 已覆盖正常取消/EOF 清场；支持矩阵同时写明 `mcp-serve` 被 SIGKILL 时子进程组可能无人收。**不能说它因此自动把写权限交给下个会话**：`WriteGuard::acquire` 会因残留 `held` 拒绝自动转移，现有策略是安全性优先、人工恢复。[S5、S8]

应补明确的进程归属证据、服务崩溃后的对账和操作员恢复路径；评估父进程死亡、脱离进程组、持管道后代和机器重启分别依赖什么机制。可采用受控 supervisor 或平台进程容器，但不能仅凭 PID、进程不存在一次或等待某个固定时长就清锁。

**验收**：故障注入后没有未登记的可写后代；做不到自动清理时，拒绝写权转移且诊断能指向准确资源与恢复步骤。不要把“超时已发送 TERM”写成“所有副作用已撤销”。不要求为这一步恢复已封存的 exec-server 实现。

### X06 / P1：能力协商应比较语义，不只比较参数名

gld `Offered` 缓存的是工具名及顶层 `inputSchema.properties` 键。它已经有效防止老 ccnm 忽略 `run_in_background`；但不检查嵌套操作、类型、枚举、必填条件与生命周期差异，不能据此宣称完整兼容。[S6]

建议保留已评审工具白名单，增加小而明确的语义能力描述：后台模式、可否 stdin/TTY、连接代次、等待上限、输出引用寿命、条件写与 notebook 操作版本。不要上来就造一个任意上游都能调用的通用网关。服务端必须自行验证输入，不能依赖只有 gld 才做的检查；外部 CLI 可绕过 hub 直连。[R2]

对影响权限或副作用的未知字段/操作要有明确拒绝契约。若改变已冻结 `/1` 的容错行为，先判断是否需要新版本或显式能力协商，不能一边宣称完全兼容、一边全局开 `deny_unknown_fields`。工具清单翻页、schema 变化后的失效和客户端重新发现也要有测试。

**验收**：新 hub 连旧 Runtime、旧客户端连新 Runtime、不支持的新嵌套操作和错误参数类型都不会静默降级；拒绝发生在执行之前，而且不误伤仍有效的 coding 会话。

### X07 / P1：hub 默认化必须以项目级授权为前置

支持既有 L1 方向：单项目命令保留为快捷入口和受限视图，默认连接收敛为 hub，而不是维护平行生命周期。**不要先删除单项目入口，再让用户用一枚能访问全部成员的凭据替代。**[S6]

授权需贯穿 workspace 枚举、context、工具、Job、output、artifact、history 与恢复操作；审批结果绑定主体、workspace、规范化操作与版本/期限，不把模型传入 `confirm: true` 单独当作操作员授权。撤销须影响实际访问与相关执行，不只是下次 UI 刷新。认证 audience 和会话归属不能因为聚合而丢失；MCP 安全指南也把代理授权与会话标识分开处理。[R3]

另一个实际问题是 `context_fingerprint` 包含名称、全局 instructions/skills 配置，而重建旧上下文会 `terminate_all`。因此“改项目说明”和“撤销执行权限”目前可能触发同一种清场。资源对象与上下文视图拆开后，按信息变更、权限变更、root/身份变更分类处理。[S6]

**验收**：一个项目的分享不能读取其他成员；猜中 Job ID 不能越权；改显示名不杀构建；撤销写授权按策略立即生效；停止分享、停止 Job、删除注册和停整个服务是不同操作。

### X08 / P1：skills 的发现、解析、激活与授权不能混成一件事

共享 `toexec-skill` 的方向正确，命令注入不自动执行也正确。其手写解析器已经明确支持 YAML 子集、拒绝部分结构并设置深度限制，不应简单评价成“没有安全意识”或立刻强制换依赖。真正需要的是可公开复验的语料、差分测试、模糊测试，以及重复键/大小写/连字符归一化的冲突规则。[S1、S2]

建议把语法结果和 provider 特定语义分层：先原样保留字段，再由产品判断哪些支持、哪些忽略及原因。特别测试 `disable-model-invocation` 与归一化别名重复、截断描述、畸形 frontmatter、嵌套列表、巨大输入。加载附件只授权已发现且明确允许的 skill 目录，不能为了用户级附件可读就放开整个 HOME。

`allowed-tools` 不能被理解为 ccnm 的远端安全白名单。当前 Claude 文档中它与 skill 激活时的免逐次审批有关，实际工具可用性还受其他权限规则控制；不要从一个字段名推断宿主约束。项目描述、提示词和脚本都是不可信内容，返回来源、作用域、内容版本并防止同名混淆；目录发现不自动批准执行。[R4]

**标准扩展需要单独校正 v3 的工作量判断。** 当前官方 Skills 扩展稳定规范基于 MCP `2026-07-28` 或更新版本，包含 `server/discover` 能力声明、Resources、完整资源清单与摘要等要求；本会话服务报告的是 `2025-06-18`。因此不能只实现两个方法就宣称“等客户端开关打开自动原生支持”。先核对协议基线、宿主版本、协商与资源身份，再决定独立阶段；已可用的工具通道继续保留。[R5]

**验收**：能够发现和读取，与模型会主动使用、宿主原生激活、脚本获得执行权限分别记账；不支持的结构明确报原因，不静默当空内容；标准扩展未经端到端协商验证不标支持。

### X09 / P1：Agent 面应恢复必要能力，但不能扩大凭据侧执行面

v3 已确定的 Web 策略不用重新征询：**WebSearch 默认开放，WebFetch opt-in**。后续实现仍须按当前受测官方 CLI 的实际工具与启动行为验证，不凭名称猜测。其他子代理、todo、提问、计划模式先作为经过验证的能力集合，不一起盲开。[S2]

受管启动采用可用工具允许集，配合已有 deny；子代理继承、动态发现工具、计划模式、模型/版本变化都必须验证。尤其不能因为恢复 Skill 或子代理，令项目脚本、hooks、项目 MCP 在持有 AI 登录的机器上执行。用户自有外部 CLI 的本地工具是否关闭由 Host 控制，ccnm 不能承诺消灭所有旁路。

文件、搜索、图片、后台命令的具体限制属于执行能力；联网检索、问用户和子代理属于 Agent 能力。将这两者分开恢复，比再补一套自建 Agent harness 更符合原目标。`exec_sandbox = codex` 是另一项可选执行依赖，native exec-server 被封存并不使这项依赖自动消失；沙箱二进制 pin、能力与 Agent 版本策略应分别记录。[S4–S5]

**验收**：只开放声明集合，未知新增内置工具默认关闭；子代理无本地文件/命令旁路；WebFetch 未 opt-in 时不可用；既有合法远端操作不退化。真实模型验证单独确认额度，不把历史实验预算自动沿用。

### X10 / P1：源码、依赖 tag、构建、部署与客户端可见能力需要一条可核对的链

当前源码/服务差异已是实际观察，不只是未来风险。[S9] 建议在诊断输出中区分源码 HEAD、运行构建 SHA、所链接共享 crate revision、配置/profile revision、实际工具集/schema 摘要、协议与远端能力代次。`server_info` 默认返回有界摘要，详细审计按需读取，避免一次排错重新注入大量历史上下文。

部署后必须从消费者角度重新发现并调用能力，不能以 `cargo build` 或 version 字符串相同作为成功。daemon 与 CLI 使用不同二进制路径、服务仍载入旧构建、客户端缓存旧 schema 都应能定位。更新已安装二进制、重启影响任务的服务仍需授权。

三仓共享依赖继续独立 tag + lock，但加一份可机器核验的集成版本清单：各仓 commit、实际解析到的共享 crate commit、MSRV、平台和 fixture 版本。干净检出、无本地 path override/缓存优势的消费者构建通过，才证明能被下一台机器复现。共享库修好不代表两个产品已升级；本轮领先上游的提交不能当作 CI 已能取得的依赖。

**验收**：拿清单能定位实际运行组合；新字段在真实连接里可见且有效；旧服务明确报缺能力；依赖发布顺序有预检，不因先推消费者再推 tag 导致干净 CI 拉不到。此处是发布方案，不授权本轮 push/tag/release。

### X11 / P2：跨平台按角色拆，不能只画三乘三的表

将 OS 能力拆成 gld 本地执行、gld hub 连接器、ccnm Runtime、ccnm Agent/Controller 四个角色。Windows 上的 gld 本地可构建，不等于 Windows 能启动目前依赖 ccnm 的 remote bridge；Linux Runtime 已跑过，不等于 Linux Agent 已可用。[S2、S4]

近期修共享库 Windows 文件安全并补原生测试，不以此扩大 ccnm Windows 范围。然后为 Windows 独立 RFC 定第一角色和真实用户价值，再评估进程容器/Job Object、信号与 stdin/PTY、路径/大小写/reparse point、ACL、可执行文件解析、服务管理和远端连接依赖。相关平台能力都需实测，不能把 Unix 进程组代码换几个条件编译就标完成。

建议先验证一个 gld 本地真实 Web 开发闭环和一个 macOS Agent/hub → Linux Runtime 闭环，再扩平台，而不是同时启动九格全面移植。用户长期三客户端三平台目标保留，未设计的格子明确写未设计。

### X12 / P2：计划与证据正在变成第二种维护成本

v2 页首已封存 native 链，但第 4 节仍有旧调用图；v3 顶部“刚立项”、G3 未开工和部分旧设计条目，已与仓库事实不同。ccnm `status.json` 本轮约 345 KB，其中 handoff 多次附带历史轮次全文。它们会使后续模型反复读取过期事实或误领旧任务。[S2–S5]

建议一个短的当前入口列有效决策、唯一进度来源、未完成依赖与证据路径；历史方案仍保存，但明确标记不再用于实施。status 保留机器可验的任务结构，handoff 只留本轮恢复点、阻塞和下一动作，历史细节归已有 research/Git，不再层层复制。改变 status 结构要同步校验器，不能直接删历史证据。

本评审的 X 编号是问题索引，后面的阶段是建议依赖，**都不是第三份进度数据库**。ccnm 仍以 `docs/plan/status.json` 为准，gld 仍承接 U/L/RFC-0003，toexec 记录共享机制与消费者采纳证据。

### X13 / P2：完整开发闭环应优先于追平工具清单

承接 gld 已有 L2/L3：项目任务发现、长命令/开发服务、受控浏览器、产物和验证证据。这些比再次争论工具名字是否等同原生更接近前端日用目标。浏览器在能访问项目服务的节点运行；远端 `localhost` 不是 hub 的 `localhost`。预览、下载和浏览器登录态不能隐式扩大网络或数据权限。[S6]

验证要绑定代码快照/工作树内容、执行环境、命令和输出完整性；测试后改代码，旧证据应过期。新 Job、截图、构建包按主体和 workspace 归属，并设置总量/保留期限。ccnm P41 活跃后台命令输出可以额外占用明显磁盘空间，限流不仅是每个请求的输出长度，还需要节点、workspace 和主体的配额。[S5]

gld 可以在模型暂时不调用时继续一个已启动进程，但它不会自行继续推理。真正无人值守多轮开发仍需显式进入官方 Agent/独立 Orchestrator 路径，不能把后台进程称为自主 Agent。

## 6. 建议实施顺序与停止点

以下 A–F 是跨仓依赖分组，实施时映射到原有计划，不建立平行状态系统。**A/B 应先做；C/D 是可靠日用的主线；E 中少量独立补齐可并行，但不能提前宣称总体完成。**

### A. 对齐基线和有效计划

负责人：三仓文档维护者，gld 负责运行能力诊断设计。

交付：纠正 v2/v3 当前入口和 gld G3 状态；列出运行构建与源码的差异；把本评审问题映射进现有 U/L/RFC/P 阶段；将“已实现/已验证/已部署”拆开。

停止条件：另一个模型不读聊天历史，也能说清当前主线、哪些旧路线不能继续、下一项未完成工作与证据在哪。禁止为了对齐数字而补写并不存在的运行验收。

### B. 文件安全与共享库消费者收口

负责人：toexec 主改 X01；gld 主改 X02；ccnm 只复核共享依赖采用及其事务/版本边界。

交付：失败不删旧目标的替换行为；元数据三态；有边界说明的版本前置条件；schema 与实现一致；共享库 Windows 原生测试与两消费者回归。

停止条件：故障用例不过就不升级受影响运行构建；没有 Windows 环境则明确 blocked，不能用 Linux 单测替代。不要借此统一两产品所有 patch/UTF-8/回滚契约。

### C. hub 资源所有权与窄授权

负责人：gld，对应 L1；ccnm 配合确认跨入口资源域。

交付：统一本地 Runtime 资源所有者；主体/grant/视图与资源分离；单项目 scoped view；目录别名/重复写注册处理；区分描述配置与安全配置变更。

停止条件：单项目分享不能越权、多个入口不会形成隐藏并行资源表，才将 hub 设为默认并清除重复生命周期代码。对真实隔离部署保留独立实例，不要求所有项目进同一 OS 进程。

### D. 生命周期和能力契约

负责人：ccnm 提供远端权威语义，gld 实施连接与观察；对应 L2/G1 后续，不是重做 G1。

交付：复现并解决后台 Job/空闲回收组合问题；明确 session-bound 与未来 durable 的区别；取消、终止、崩溃未知、租约与输出配额；补工具语义协商与服务端检查。

停止条件：跨 HTTP/MCP/SSH 的异常不造成隐式重放、误报成功或静默丢任务；无法证明结束时保留未知与写权保护。改变冻结生命周期前必须有新版本或显式协商设计。

### E. 剩余能力与 Agent 恢复

负责人：gld G3.2；ccnm 新阶段；toexec 仅补真实需要的 parser 测试/机制。

交付：gld notebook；skills 原有工具通道的附件/冲突/预算测试；ccnm 最小 Agent 能力允许集和既定 Web 策略。标准 Skills 扩展、其协议升级单独立项，不塞进一次普通工具加法。

停止条件：能解释每项能力在哪台机器执行、凭据在哪、宿主实际收到什么；真实模型是否会用单独验。PDF、hooks、项目 MCP 自动执行、LSP 全栈和第三方 harness 不自动加入范围。

### F. 真实闭环、集成版本与平台扩展

负责人：三仓联合验收，gld 对应 L3；Windows 后续单独 RFC。

交付：一个 TypeScript Web 项目和一个 Rust CLI fixture 的完整流程；一次 gld 本地、一次 hub→ccnm、一次官方 Agent→ccnm 的证据；干净检出构建与消费者版本清单。

停止条件：任一链路失败，不将其他链路成功复制为它的通过证据。先固定少量代表性场景，再按已授权预算扩大模型对照；操作员批准后才部署/发布。没有真实浏览器和网络条件就写未验，不以截图存在代替交互验收。
